# TokenOps 智能运营平台项目立项书

编制日期：2026-06-09  
适用场景：江苏电信分公司 AI 项目竞赛、创新项目申报、路演材料前置文档  
项目阶段：10 天二次开发 MVP

## 1. 项目名称

**TokenOps 智能运营平台：面向大模型应用的成本、限流与故障定位助手**

项目简称：**TokenOps**

一句话定位：  
面向企业内部不断增长的大模型应用，把 Token 消耗、模型调用质量、异常故障、应用成本分摊和限流策略统一纳入可观测、可解释、可治理的 AI 运营闭环。

## 2. 项目背景

江苏电信正在从“AI 能用”进入“AI 规模化运营”阶段。随着内部智能体、客服助手、装维助手、云网运维助手、办公助手等应用持续增长，大模型调用量和 Token 消耗会快速放大。此时，企业面临的核心问题不再只是“能不能调用大模型”，而是：

- 哪些应用消耗了最多 Token？
- 哪些 Prompt 成本高但效果差？
- 哪些应用在高峰期拖慢整体服务？
- 哪些模型调用失败、超时、重复请求，导致业务投诉或成本浪费？
- 多部门、多地市、多应用共用模型能力时，成本如何核算与分摊？
- 出现异常波动后，运营人员如何快速定位是模型、网关、应用、Prompt、知识库还是用户行为的问题？

公开资料显示，江苏公司已在探索 Token 运营，关注大模型应用的流控、计费、故障定位、成本分摊等问题。中国电信集团层面也发布了 TokenHub 相关能力，说明 Token 管理正在成为运营商 AI 规模化落地中的基础能力。



## 3. 目标用户

### 3.1 直接用户

1. **省公司 AI 运营团队**
   - 关注全省大模型能力调用、Token 成本、异常波动、应用接入质量。
   - 需要看全局指标、定位异常、输出运营月报。

2. **地市公司 AI 应用负责人**
   - 关注本地市 AI 应用的调用量、成功率、成本、体验质量。
   - 需要知道哪些业务消耗高、哪些场景应优化 Prompt 或切换模型。

3. **云网运维与装维支撑团队**
   - 关注智能体是否稳定回答、故障定位是否准确、知识库命中是否有效。
   - 需要在系统异常时快速定位链路问题。

4. **财务与经营分析人员**
   - 关注成本核算、部门分摊、应用投入产出比。
   - 需要按应用、部门、地市、模型生成账单和分摊报表。

5. **AI 应用开发团队**
   - 关注 Prompt 质量、模型路由、调用失败、延迟和上下文长度。
   - 需要基于数据优化应用。

### 3.2 间接受益用户

- 客服人员：获得更稳定的智能辅助回答。
- 装维人员：减少无效 AI 问答和重复查询。
- 政企客户经理：获得成本可控、响应更稳的 AI 能力。
- 管理层：掌握 AI 应用真实使用量、价值和风险。

## 4. 核心问题

### 4.1 成本不可见

大量 AI 应用接入模型后，调用成本被隐藏在网关、平台或共享账号之后。没有统一的 Token 统计，管理者很难回答：

- 本月 Token 总消耗是多少？
- 哪个应用、部门、地市消耗最高？
- 哪些请求是无效消耗？
- 成本是否和业务价值匹配？

### 4.2 限流不可控

AI 应用峰值调用时，容易出现模型网关拥塞、响应延迟升高、失败率上升。如果没有精细化限流策略，只能粗放处理：

- 全局限流影响关键业务。
- 单应用过载拖垮共享模型资源。
- 高成本模型被低价值场景占用。
- 异常脚本或循环调用造成 Token 泄漏。

### 4.3 故障定位慢

大模型调用链路跨越应用、Prompt、知识库、模型网关、模型服务、计费系统、网络链路等多个环节。发生故障时，传统排查方式依赖人工查看日志，定位慢、协同成本高。

典型问题包括：

- 成功率下降，不知道是模型不可用还是应用参数错误。
- 平均延迟上升，不知道是上下文过长还是模型排队。
- 回答质量下降，不知道是知识库召回差还是 Prompt 变更。
- Token 消耗突增，不知道是业务增长还是异常重试。

### 4.4 运营闭环缺失

很多平台只能展示指标，无法进一步给出建议。运营人员看到异常后，仍然要自己判断：

- 是否应该降级模型？
- 是否应该调整限流阈值？
- 是否应该优化 Prompt？
- 是否应该更新知识库？
- 是否应该向应用负责人发起工单？

本项目希望从“指标展示”推进到“智能分析 + 策略建议 + 报告生成”。

## 5. 项目目标

### 5.1 总体目标

建设一个面向大模型应用的 Token 运营智能平台，实现对模型调用日志的采集、统计、分析、异常定位、成本分摊、限流建议和运营报告生成，帮助江苏电信在 AI 应用规模化阶段实现可管、可控、可优化。

### 5.2 10 天 MVP 目标

十天内完成可路演版本，重点不是接入全部真实系统，而是打通完整业务闭环：

1. 支持导入或模拟大模型调用日志。
2. 展示 Token 消耗、调用量、成本、延迟、失败率等核心指标。
3. 支持按应用、部门、地市、模型维度统计。
4. 自动识别异常应用和异常 Prompt。
5. 基于规则和 RAG 知识给出限流、降级、Prompt 优化建议。
6. 支持自然语言提问，例如“本周哪个应用成本异常？”。
7. 生成成本分摊账单和异常分析报告。
8. 在路演中演示“发现问题 -> 定位原因 -> 给出策略 -> 生成报告”的闭环。

### 5.3 后续建设目标

1. 接入真实模型网关日志、应用日志和计费数据。
2. 与统一认证、工单系统、运维平台打通。
3. 构建实时告警与自动策略下发能力。
4. 建立多模型路由和预算控制策略。
5. 支持省、市、部门多级运营视图。

## 6. AI 能力

### 6.1 RAG 运维知识问答

平台内置 Token 运营知识库，包括：

- 模型调用规范。
- Token 计费规则。
- 限流策略说明。
- 常见错误码。
- Prompt 优化规范。
- 应用接入手册。
- 故障排查 SOP。

用户可以用自然语言提问：

- “为什么客服助手昨天晚上失败率升高？”
- “哪个应用最适合从高成本模型降级到小模型？”
- “如何设置装维助手的峰值限流策略？”

系统回答时给出证据来源，避免黑盒建议。

### 6.2 智能异常检测

平台基于日志指标识别异常：

- Token 日消耗突增。
- 单次请求上下文过长。
- 重试次数异常。
- 成功率下降。
- 平均延迟升高。
- 某应用调用量异常放大。
- 高成本模型被低价值场景频繁调用。

MVP 阶段优先采用规则阈值 + 同比/环比波动判断；后续可以加入时间序列模型和无监督异常检测。

### 6.3 故障定位智能体

系统将异常指标、调用日志、错误码、应用信息、知识库规则组织成诊断链路，输出结构化结论：

- 异常等级。
- 影响范围。
- 疑似根因。
- 证据片段。
- 建议动作。
- 责任归属。
- 建议工单标题和描述。

示例输出：

> 客服知识问答应用在 20:00-21:00 失败率从 1.2% 升至 8.6%，主要错误为 context_length_exceeded。异常请求集中在“政策全文总结”Prompt，平均输入 Token 达 28k。建议对该 Prompt 增加摘要压缩步骤，并将最大上下文限制调整为 12k。

### 6.4 成本分摊与预算建议

平台根据模型单价、输入 Token、输出 Token、调用次数计算成本，并按应用、部门、地市、业务线生成分摊视图。

MVP 阶段使用配置化模型单价和模拟日志；后续接入实际计费系统。

输出能力包括：

- 应用成本排行。
- 部门成本分摊。
- 单次请求平均成本。
- 高成本 Prompt 清单。
- 预算超限预警。
- 月度账单导出。

### 6.5 限流与模型路由建议

平台根据业务优先级、应用成本、失败率、延迟和预算给出策略：

- 限制低优先级应用峰值 QPS。
- 为高价值业务预留模型额度。
- 将低复杂度任务路由到小模型。
- 对超长上下文请求先摘要再调用。
- 对异常重试应用进行熔断。

MVP 阶段输出建议文本和策略 JSON；后续可对接网关执行策略。

### 6.6 自动报告生成

系统支持一键生成：

- Token 日报。
- 应用成本榜单。
- 异常分析报告。
- 限流策略建议书。
- 经营分析简报。
- 路演用运营态势摘要。

报告强调“数据 + 原因 + 建议 + 预期收益”。

## 7. 项目价值

### 7.1 对江苏电信的价值

1. **把 AI 应用从建设阶段推进到运营阶段**
   - 不只关注应用上线数量，更关注调用质量、成本效率和稳定性。

2. **支撑全省 AI 应用规模化治理**
   - 面向多地市、多部门、多模型、多应用统一运营。

3. **降低大模型调用成本**
   - 识别高成本 Prompt、异常重试、低价值高消耗场景。
   - 推荐模型降级、上下文压缩和限流策略。

4. **提升故障定位效率**
   - 将多源日志和知识库关联，减少人工排查时间。

5. **形成可复制的行业能力**
   - 未来可以作为天翼云、政企客户、行业智能体平台的运营组件输出。

### 7.2 对竞赛路演的价值

1. **紧扣热点**
   - 大模型应用越多，Token 运营越关键，主题贴近电信当前 AI 规模化痛点。

2. **容易演示闭环**
   - 输入日志，发现异常，定位原因，生成策略和报告，现场效果直观。

3. **区别于普通问答机器人**
   - 平台不是一个单点智能体，而是管理多个 AI 应用和智能体的运营系统。

4. **复用现有项目能力**
   - 原项目的 RAG、日志反馈、证据引用、任务编排能力可直接迁移。

5. **十天可落地**
   - MVP 可基于模拟日志和本地知识库完成，不依赖复杂外部系统联调。

## 9. 二次开发可行性

### 9.1 可复用能力

现有 `RagAgentEDA` 项目具备以下基础能力：

- 文档扫描、切块、向量化和重排。
- RAG 问答和证据引用。
- Query Rewrite。
- 问答历史和反馈记录。
- FastAPI 服务。
- Gradio 前端入口。
- 任务编排和执行链路。

这些能力可以直接用于 TokenOps 的知识库问答、策略生成、报告生成和运维解释。

### 9.2 需要新增能力

1. Token 调用日志数据模型。
2. CSV/JSON 日志导入。
3. 指标聚合计算。
4. 异常规则引擎。
5. 成本配置和分摊逻辑。
6. 策略建议生成器。
7. TokenOps 专属前端页面。
8. 报告导出。

### 9.3 十天开发策略

十天内应优先做“能讲清、能演示、能闭环”的功能，不追求真实系统全量接入。

| 天数 | 目标 |
| --- | --- |
| 第 1 天 | 明确数据字段、准备模拟日志、整理 Token 运营知识库 |
| 第 2 天 | 增加日志导入和 SQLite 存储 |
| 第 3 天 | 实现指标聚合和成本计算 |
| 第 4 天 | 实现异常检测规则 |
| 第 5 天 | 实现故障定位解释和策略建议 |
| 第 6 天 | 接入 RAG 问答和报告生成 |
| 第 7 天 | 开发 TokenOps 前端页面 |
| 第 8 天 | 打磨演示数据和端到端流程 |
| 第 9 天 | 准备路演材料、录屏和备份方案 |
| 第 10 天 | 联调、压测、彩排 |

## 10. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 无法接入真实日志 | 演示真实性不足 | 使用脱敏样例和模拟日志，强调接口可替换 |
| 成本单价不确定 | 成本计算不精确 | 使用配置化单价，标注为演示测算 |
| 大模型调用不稳定 | 问答和报告生成受影响 | 保留规则模板和本地报告兜底 |
| 范围过大 | 十天无法完成 | MVP 只做日志分析、异常定位、策略建议、报告生成 |
| 前端开发时间不足 | 路演效果弱 | 使用 Gradio 快速搭建工作台 |
